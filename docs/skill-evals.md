# Skill evals

Self-maintained skills use two versioned artifacts:

- `evals/evals.json` defines prompts, fixtures, and grader assertions.
- `evals/verification.json` is generated by a baseline/current run and binds the result to the skill version, skill digest, eval digest, baseline ref, run id, counts, time, and external workspace.

The machine-readable schemas live in `schemas/`; `examples/skill-evals/evals.json` is a complete suite example.

## Runner protocol

`spells skill eval run` starts the executable supplied by `--runner` once per case and variant. The executable receives one JSON object on stdin and emits one JSON object on stdout. Its input has exactly `prompt`, `fixture`, and `skill` fields.

The skill snapshot excludes `evals/`, so the tested agent never receives expected values or assertions. External-system suites must state mock-only execution in `evaluation_protocol`; otherwise the run is rejected before the runner starts.

```bash
spells skill eval run workflow/example \
  --baseline-ref HEAD^ \
  --baseline-dir /tmp/example-baseline \
  --runner ./scripts/codex-skill-eval-runner.mjs

spells skill eval audit --baseline-ref HEAD^
```

For a brand-new skill, omit `--baseline-dir` and use an explicit empty ref such as `--baseline-ref empty:new-skill`. The runner rejects empty baselines paired with Git-looking refs, and rejects materialized baselines paired with empty refs.

Detailed inputs, outputs, and grading remain under `~/.sync-spells/eval-runs/` by default. Only the compact verification file belongs in the skill directory.

The bundled Codex adapter never starts an agent for the empty new-skill baseline. For current snapshots it runs Codex in read-only, ephemeral mode and asks for a structured simulated result. Set `CODEX_BIN` when `codex` is not on `PATH`.

## Gate behavior

- `spells skill new` creates an empty suite skeleton that must be completed and run before sync.
- `spells push` treats every discovered skill as changed and blocks missing, invalid, stale, unsafe, or failed verification.
- `spells sync` compares the registry with `HEAD^`, includes working-tree and untracked changes, and applies the same blocking rules to changed skills.
- Untouched historical skills without evals produce warnings only. `.system`, `third-party`, `third_party`, and `vendor` trees are excluded.
